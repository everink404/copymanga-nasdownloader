## 必改

### M1：明确所有旧源记录的保留边界，不只承诺 CopyManga

证据：`dispatcher.py:11` 与 `updater/updater.py:14` 均登记 copymanga、terra_historicus、antbyw、ganganonline、bilibili 五个源。S0 第 2 节只明确“旧 CopyManga 数据保留且可停用”，第 5 节虽要求旧 JSON 备份、幂等导入和回退，但没有说明其他旧源在新架构中的支持状态。

风险：首版仅启用嬉皮合理，但不能让“只接入一个源”被理解成可丢弃其他源记录、未知字段或历史任务。也不能反过来默认为必须把五个旧源全部重写，导致范围膨胀。

最低修订：声明所有既有源及未知源记录原样保留；未适配的源显式停用并说明原因，不自动入队、不假报无更新、不静默删改。是否继续提供旧源运行能力由入口列为待决定，不把适配所有旧源设为 MVP 条件。S1 备份/兼容清单覆盖配置、订阅、任务历史、已有 CBZ 与临时图片之间的引用关系；对不迁移的数据明确保留方式。

处置责任：入口修订 S0 的范围及兼容要求；S1 制定具体兼容路径。退出证据：定义中可明确回答“升级后旧的非 CopyManga 记录在哪里、处于什么状态”。

### M2：补入 CBZ 与完成记录不一致时的恢复要求

证据：`downloader.py:114` 原子替换 CBZ，`downloader.py:116` 随后删除章节临时目录；`plugins/copymanga/main.py:115` 才写完成记录。该处已处理写记录失败并返回失败，但仅凭这一顺序不能证明崩溃后的恢复或重复执行安全。`downloader.py` 按作品名和章节文件名生成输出，现有路径不能直接证明归属身份。

S0 第 8 节已要求“打包或记录写入失败不虚报完成”，这是正确要求；仍缺少明确的下一次执行规则：CBZ 已保存但记录未落盘时，既不能凭文件名推定已完成，也不能无条件覆盖旧产物或要求重新联网才能恢复本地事实。

最低修订：增加“产物已落盘而完成记录失败/进程中断时，保留可核对身份和内容的恢复证据；重启或重试须安全对账，不能误认同名旧文件或破坏既有产物”。将该窗口以及反向的“记录声称完成但产物缺失/损坏”列入 S1 正反样例、S2 故障夹具与退出条件。具体采用清单、事务日志或其他方法留给 S1。

处置责任：入口补保护要求；S1 定义成功提交/恢复顺序，S2 在获准后验证。此项属于现有可靠下载要求，不新增产品功能。
